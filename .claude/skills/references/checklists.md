## DDD

| Проверка | Плохо | Хорошо |
|---|---|---|
| Домен без технологий | `import { readFile } from 'node:fs'` в `domain/` | I/O только в `infrastructure/` |
| Единый язык | `processData(d: any)` | `confirmOrder(order: PendingOrder)` |
| Инварианты в типе | проверка суммы в трёх вызывающих | приватный конструктор + `Order.create()` |
| Value Object вместо примитива | `email: string` | `type Email = string & { __brand: 'Email' }` + `parseEmail` |
| Явные границы контекста | одна папка `utils` на всё | папка на поддомен |

Признак анемичной модели: тип — только поля, все правила в `*Service`. Для скрипта допустимо; для долгоживущего домена — замечание.

## SOLID

### SRP
Спроси: «по каким причинам этот файл будут править?». Две причины (изменился формат отчёта / изменился провайдер данных) → разделить.

### OCP
```ts
// плохо: каждый новый формат правит существующий код
switch (fmt) { case 'csv': ...; case 'json': ... }

// хорошо: расширение через добавление записи
const writers: Record<Format, ReportWriter> = { csv: csvWriter, json: jsonWriter };
```

### LSP
Нарушение, если реализация порта: бросает там, где контракт не предполагает; требует более узкий вход; возвращает `undefined` вместо обещанного массива. В TS часто ловится включением `strictFunctionTypes`.

### ISP
Порт с 7 методами, из которых сценарий использует 2 → разбить на `OrderReader` и `OrderWriter`.

### DIP
```ts
// плохо
import { pool } from '../infrastructure/db';
export async function run() { const rows = await pool.query(...); }

// хорошо
export async function run(deps: { orders: OrderRepository; log: Logger }) { ... }
```
Диагностика по тестам: много `vi.mock('...')` = DIP нарушен.

## KISS

Пороговые значения (ориентиры, не догма):
- длина функции > 30 строк
- вложенность > 2
- цикломатическая сложность > 10
- параметров > 3 (заменить объектом)
- дженериков в сигнатуре > 2

```ts
// плохо
type DeepPartial<T> = T extends object ? { [K in keyof T]?: DeepPartial<T[K]> } : T;
// если нужен ровно один уровень — используй Partial<T>
```

Ранний возврат вместо else-лестницы; `for...of` вместо цепочки из пяти `reduce`.

## DRY

DRY — про **знание**, не про символы.

Настоящее дублирование: одно правило («НДС 20%», «телефон в формате +7…», ключ env) записано в нескольких местах — при изменении надо помнить обо всех.

Ложное срабатывание: два `map` с похожей формой, но разными причинами изменения. Склеивание создаёт связность и параметр `isAdmin: boolean`, который потом обрастает ветками.

Правило трёх: выносим на третьем повторении, не на втором.

## YAGNI

Красные флаги:
- интерфейс/фабрика/плагин-система с одной реализацией
- параметры `options`, которые всегда передаются одинаково
- `export`, не используемый ни одним импортом (`npx ts-prune`)
- обработка форматов/кейсов, которых нет в требованиях
- «пока закомментируем, потом пригодится» — удалять, git помнит

Контраргумент, когда YAGNI не применяем: точка расширения дешева сейчас и дорога потом (границы процесса, формат хранения данных, публичный API).

## Конфликты принципов

Принципы тянут в разные стороны — фиксируй выбор явно:

| Конфликт | Разрешение |
|---|---|
| SOLID (абстракция) vs KISS/YAGNI | Абстрагируй только там, где вторая реализация уже видна или где нужен шов для тестов |
| DRY vs связность | Дублирование дешевле неправильной абстракции; предпочитай дубль до третьего случая |
| DDD-слои vs размер скрипта | Для < 200 строк допустимы слои-секции в одном файле, но с сохранением портов |

В отчёте аудита такие компромиссы выноси в раздел «Осознанно НЕ рекомендую менять».
